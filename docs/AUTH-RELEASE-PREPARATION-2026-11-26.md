## Зависимости и порядок интеграции

Перед выпуском подготовить согласованные манифесты, branch aliases и
changelogs, обновить README и migration notes. Не публиковать одновременно
несогласованные пакеты: сейчас их манифесты всё ещё требуют core ^3.0
и session-http ^2.0.1. Для поддерживающих оба core major пакетов добавить
^3.0 || ^4.0, для использующих оба session-http major — ^2.0.1 || ^3.0,
только после проверки обеих комбинаций. Если старая комбинация не поддерживается
или прежний API нарушается, пересчитать major соответствующего пакета.
Нижние границы зависимостей должны отражать фактически необходимые исправления:
в частности session-database должен использовать исправленный session для
numeric metadata; межпакетные тесты с отложенной публикацией должны проверять
согласованные версии auth-http и session-http. Не оставлять заявленными
непроверенные диапазоны только ради прохождения solver.

Рекомендуемый топологический порядок:

1. Совместимый с Config 4 stable Identity (отдельная работа) и stable DI 6
   для app-адаптеров; Clock уже совместим.
2. auth, auth-token.
3. auth-http, auth-session.
4. auth-session-database, auth-session-http.
5. auth-jwt, auth-password, auth-magic-link, auth-otp, auth-recovery-code,
   auth-remember-me, auth-totp, auth-webauthn.
6. auth-app и auth-session-app.

Нужно повторить полные Composer resolve/install, PHPStan, PHPUnit/Pest и
обязательный mutation gate session-http на согласованном наборе веток,
а затем на реальных опубликованных версиях. Прежняя матрица
Config 3 / DI 5: 560 passes из 564 выбранных, 2578 assertions —
это исторический baseline, а не новый результат данного прохода.
Четыре native DB-теста ранее пропущены, два OTP-кейса исключены; эти
ограничения сохраняются. Не утверждать проверку MySQL/PostgreSQL или
browser/hardware WebAuthn, если они не выполнены. Сначала применить
WebAuthn revision migration на существующей БД, затем выкладывать код.
После подтверждённого прохождения gates интегрировать проверенные ветки,
создать новые теги от точных SHA и релизы с changelog/migration notes,
затем проверить доступность в Packagist и установку целевой комбинации.

Никакие существующие теги не перезаписывать. Архивный auth-session-csrf
не получает новый релиз. Отдельные тестовые коммиты сами по себе не требуют
релиза; app-адаптеры получат новые версии для подтверждённой совместимости.
